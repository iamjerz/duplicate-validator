# duplicate-validator

## Status column (Results table)

Each rule's Duplicate Groups table has a "Status" column. For a flagged (non-UNIQUE) group, this no longer shows the engine's own internal `DUPLICATE`/`POTENTIAL_DUPLICATE` labels - it shows that rule's own duplicate type instead: "True Duplicate" or "Potential Duplicate" when the rule's Analysis resolves to one of those (see `classifyDuplicateType`), or the rule's own uploaded file name when it doesn't (e.g. a rule with a custom Analysis string, or none at all) - the same fallback the Results page's tab titles already use when a rule has no recognized Analysis. Both the label AND the badge color are the same for every flagged row in one rule's tab, since they describe which rule/kind of match that whole tab represents, not a per-group computation - a "True Duplicate" rule can still produce individual groups where some UNIQUE field differs (those stay distinguishable via the "Different UNIQUE Fields" and "Explanation" columns). The badge is red for a True-Duplicate rule, amber for a Potential-Duplicate rule (its original color, unchanged), and gray for a rule whose Analysis doesn't resolve to either. A UNIQUE group is never a duplicate of any type, so it always keeps its own plain "Unique" label and green badge regardless of rule. See `classifyDuplicateType`/`DUPLICATE_TYPE_LABELS` in `src/engine/DuplicateTypeClassification.ts` and `buildDuplicateGroupColumns` in `src/components/DuplicateTable/columns.tsx`.

The status filter checkboxes above the table, the KPI cards, and the "Record Breakdown" pie chart (all on the Results page) follow this same rule-driven label instead of the raw engine distinction too, for the same reason: since every flagged row in a rule's tab already reads the same type in the Status column, a control still split into separate "Duplicate" and "Potential Duplicate" buckets would show a count or a checkbox that doesn't correspond to anything a reviewer can actually tell apart in the table. So there are only ever two checkboxes per rule's tab - the rule's own type label (e.g. "True Duplicate") covering every flagged group regardless of its own raw status, and "Unique" (never removed) - and the KPI cards/chart combine what used to be separate "Duplicates" and "Potential Duplicates" figures into one number under that same label, colored the same way (red/amber/gray). Uploading two rules of different types (say, a True-Duplicate rule and a Potential-Duplicate rule) shows "True Duplicate" + "Unique" on one rule's tab and "Potential Duplicate" + "Unique" on the other's, rather than a generic "Duplicate" label on both - across the tabs you've uploaded, you see exactly the distinct types those rules actually represent. See `resolveDuplicateTypeLabel` in `src/engine/DuplicateTypeClassification.ts`, `displayStatusOf` in `src/components/DuplicateTable/DuplicateTable.tsx`, and `src/components/ValidationSummary/ValidationSummary.tsx`.

Note: the Group Details modal (opened by clicking a row) is a separate view and still shows the raw `DUPLICATE`/`POTENTIAL DUPLICATE`/`UNIQUE` engine status with its original color scheme - it hasn't been changed to match the table above.

The same table also has an identifier column next to "Root Id", and which field(s) it shows depends on the rule's own level (its `"level"` metadata text, resolved via `classifyRuleLevel` in `src/engine/RuleLevelClassification.ts` - same case/punctuation-insensitive matching as the Status column above): an Invoice-level rule (or one whose level is missing or unrecognized) keeps a single "Invoice Number" column, unchanged; a Shipment- or Charge-level rule shows "Tracking Number" and "Bill Of Lading" instead - the identifiers that actually distinguish a shipment or charge record (several different invoices can share one shipment/charge, and vice versa). Both of the new columns read the group's first record's raw cell value directly from the dataset rather than from the rule's own SAME-field bookkeeping - "Bill Of Lading" in particular is a UNIQUE (or even uncompared) field rather than a SAME field in every real Shipment/Charge rule this app ships with, so it would never show anything if it only looked at matched SAME values the way "Root Id"/"Invoice Number" do. See `buildDuplicateGroupColumns` in `src/components/DuplicateTable/columns.tsx`.

## Blank-looking placeholder values ("-")

Some source systems (this app was built against freight-invoice audit exports) use a lone dash as their universal "no value" token in a cell - across string, date, and amount columns alike - instead of leaving the cell genuinely empty. A cell containing nothing but dashes once trimmed (`-`, `--`, `" -   "`) is now treated as blank, the same as an empty or whitespace-only cell.

This matters most for SAME fields that are only populated while a record is in some active status - for example, an "Approved Amount" column that carries a real figure for an OPEN record but a dash placeholder once that same record is VOID or CLOSED. Without this, a voided record and its still-open duplicate would be compared as the literal strings `"-"` vs `"578.04"` and never match, even though the dash was never meant to be a real value at all.

A SAME field with a detected blank (dash-placeholder or otherwise) gets its "Allow blank" checkbox pre-checked in the Column Mapping panel - override it per field at any time. Enabling it promotes that field from a required exact match (SAME) to a comparison-only field (UNIQUE): records can still group together without it matching, and a genuine difference (including blank vs. a real value) downgrades a match from "Duplicate" to "Potential Duplicate" rather than being silently ignored.

## Chained "Root Id" references

A rule whose SAME fields include "Root Id" no longer requires every record in a family to carry the exact same Root Id value. In a multi-hop duplicate chain, one record's Root Id can point at a sibling record's own identifying value (its UNIQUE field, e.g. "Invoice Id") instead of at the family's ultimate shared root - record C's Root Id might equal record B's Invoice Id, while record B's Root Id equals record A's Invoice Id, so A/B/C are one family even though C's Root Id never literally equals A's.

Grouping now follows that chain: two records are only ever considered for chaining when they already agree on every OTHER SAME field (Invoice Number, Client Code, Amount, and so on), so a coincidental ID overlap between two genuinely unrelated invoices can never merge them. A rule that does not use a field literally named "Root Id" is completely unaffected. See `src/engine/ChainedFieldResolver.ts` for the implementation.

## Disposition

A reviewer can record one Disposition per duplicate group, per rule (Carrier Review, Client Review, Continue Processing, Reject Charge, Reject Invoice, Reject Shipment, Trax Review) from the dropdown in the group's detail view. It's a session-local label only - it never changes a group's DUPLICATE/POTENTIAL_DUPLICATE/UNIQUE classification or any KPI count. At export time, any record whose Disposition is set, and that has a non-blank "Audit ID" and an "Audit Exception Status" of Open, gets its Disposition written into the file's own existing "Add Action" column.

Every flagged group (DUPLICATE or POTENTIAL_DUPLICATE) is now pre-filled with a default Disposition the moment a validation run completes, based on which rule produced it: a rule whose Analysis is "Potential Duplicate" seeds `Carrier Review`, and a rule whose Analysis is "True Duplicate" (matched by substring, so "True Duplicate for denial" counts too) seeds the level-appropriate rejection - `Reject Invoice`, `Reject Shipment`, or `Reject Charge` - read from the rule's own `"level"` field (e.g. `"Invoice_level"`); a rule with a missing or unrecognized level falls back to `Reject Shipment`. A rule with no recognized Analysis, and UNIQUE groups under any rule, get no automatic Disposition. This is only a default - the dropdown still shows it as a normal selection, and picking a different option overwrites it exactly as if it had been manually set from the start. See `src/engine/AutoDisposition.ts`.

A group's default can be further downgraded to `Continue Processing` by a disposition override - see the next section.

## Disposition overrides ("this isn't really a duplicate")

A rule's SAME/UNIQUE fields can correctly cluster a group of records that, on closer inspection, isn't really the same invoice/shipment/charge - a coincidental Invoice Number collision between two unrelated clients, say. `src/engine/DispositionOverride.ts` catches the specific, evidence-backed patterns below and downgrades the default Disposition (and auto-Comment, under the fixed label "Not Duplicate") to `Continue Processing`. Every pattern here was reverse-engineered from a manually-reviewed ground-truth file (all three levels, 260 rows) rather than guessed at - and where the ground truth didn't show a clean, generalizable signal, the gap is disclosed below rather than papered over with a rule fitted to one or two examples.

**Invoice and Shipment:**

- A genuinely different Carrier Code anywhere in the group.
- A genuinely different Invoice Account Number - but only when Client Code matches across the group. Account Number is frequently just Client Code's own prefix baked into the string (e.g. `ABVNDSVDEEUR` vs `ABVEDSVDEEUR` for the "ABVN"/"ABVE" client pair), so when Client Code already differs, an Account Number difference adds no independent signal.
- **Shipment only:** a member whose own Audit Exception Status is "Open" carries an Audit Condition of exactly "Duplicate Shipment Different Charges" - a literal category the source system already assigns, 100% Continue Processing in the ground truth with zero exceptions. The superficially similar "Duplicate Shipment Different Lane" is deliberately *not* used this way - that label is a mix of real Carrier-Review cases and Continue-Processing cases, not a clean signal on its own. Audit Condition is only trusted on an Open record because the other side of a pair can carry its own, unrelated, already-resolved (CLOSED) Audit Condition that has nothing to do with the live case.

**Charge:**

- A member's Correction Indicator reads "CORRECTION" (case/whitespace-insensitive).
- A reversing (credit) entry exists *elsewhere in the file* - not a member of this group - sharing the same Tracking Number and Charge Code but carrying the exact negated Charge Amount. This is the mechanical fingerprint of a void-and-rebill: the original charge gets reversed by a separate row under a different Invoice Number, then rebilled under a third Invoice Number reusing the original amount. Checked against the whole dataset (indexed once per validation run, not rescanned per group, so this stays fast on large files).

**Known, disclosed gaps** (confirmed against the ground truth, not fixable from this file's own columns):

- Invoice rows whose comment references a "Dup Reference Id" pointing at another submission's outcome ("Previous submission was REJECTED/VOIDED") - that prior submission's own resolution lives outside this file.
- A single Invoice true-duplicate case resolved by the reviewer checking an external payment system (a specific check number and payment date) rather than anything visible in this file.
- A handful of Shipment "Different Lane" cases that are still Continue Processing despite matching Carrier/Account and not being labeled "Different Charges" - the reviewer's comment cites a specific line-item charge code (e.g. "Address Correction (AAJ.007)") or an EDI segment code, neither of which generalizes cleanly from a couple of examples.
- Charge "offset" cases where the referenced reversing invoice isn't actually present in this particular file extract (confirmed by its absence, not just unmatched) - the pattern above catches the same scenario whenever the reversing row *is* present.

Against the full ground-truth file (`Manual Validation.xlsx`, 260 rows across all three levels, 110 of them flagged for review by the human reviewer), the current rules plus these overrides match 95 of those 110 flagged rows exactly (Invoice 44/49, Shipment 38/43, Charge 13/18); every remaining mismatch is one of the gaps listed above.

## Comments

A reviewer can also record one free-text Comment per duplicate group, per rule, from the text box next to Disposition - session-local, never affects classification, and (like Disposition) is written into the exported file's own "Add Comments" column for any record with a non-blank "Audit ID" and an "Audit Exception Status" of Open.

Comments are auto-filled the same way Disposition is, following this client's own established format: `Initials: MMDDYY : Type : Reason` - for example `JDC: 101626 : True Duplicate : Same Invoice No., Client Code, and Carrier Code; Invoice Amount and Invoice Status differ.` (note the asymmetric spacing: no space before the first colon, a space-colon-space between every segment after it). The pieces:

- **Initials** come from the "Reviewer" field in the header (top right of every page) - a one-time setting, persisted in the browser, that any auditor using this app sets to their own full name (e.g. "Juan Dela Cruz"). Initials are the first letter of each word, uppercased (e.g. "JDC"). Until a reviewer name is set, no comment is auto-filled at all, for any rule - but this isn't a one-time chance: if validation was run before a name was set (or before it was corrected), setting or changing the Reviewer field backfills a comment for every flagged group that doesn't already have one yet. The Reviewer field has no debounce - it updates on every keystroke - so typing a brand-new name into it fires this backfill repeatedly as each letter goes in (e.g. "J", then "Je", then "Jer", ...). Rather than locking in whatever the very first keystroke produced (a bare "J:" from just the first letter) for the rest of the session, each pass recognizes a comment that still exactly matches what the *previous* keystroke's name would have produced and lets only that one catch up to the latest name - so the comment correctly settles on "JC:" once the full "Jerramy Calites" is typed, rather than getting stuck at "J:". A comment that's been hand-edited to anything else (by the reviewer typing over it, not by auto-fill) is left alone no matter how many more times the name changes afterward - auto-fill can only ever catch up its own earlier guesses, never overwrite what a reviewer actually wrote. See `refreshAutoComments` in `src/engine/AutoComment.ts` and the `reviewerName` effect in `ValidationSessionContext.tsx`.
- **MMDDYY** is today's date (the date the group was validated), with no separators.
- **Type** is "True Duplicate" or "Potential Duplicate", from the same Analysis matching AutoDisposition uses.
- **Reason** is built fresh for each specific group, from that group's own matched SAME fields and genuinely-differing UNIQUE fields (the exact same per-pair evaluation the Group Details explanation already shows) - not a single canned sentence reused for every group a rule flags. A group where every compared field agrees reads as `Same A, B, and C.`; one where some UNIQUE field(s) actually disagree reads as `Same A, B, and C; D and E differ.` (singular "differs" for exactly one field). Two groups flagged by the identical rule can therefore read differently, because each sentence is grounded in that pair's own values. A rule is eligible for auto-commenting purely by its `"Analysis"` text resolving to a known type (the same `classifyDuplicateType` check AutoDisposition and the Status column use) - a rule with no recognized Analysis gets no auto-filled comment (there's no "True Duplicate"/"Potential Duplicate" label to put in it), but a rule's optional `"CommentReason"` field is no longer required, or even read, for this: a real rule file that predates that field, or never had it set, still gets auto-filled comments as long as its Analysis is recognized. When a group's disposition is overridden instead (see "Disposition overrides" above), the Reason is that override's own explanation text under the fixed type label "Not Duplicate", taking priority over the field-based sentence.

This is only a default - the text box is a normal, freely-editable field, and typing over it (e.g. to add case-specific detail like a payment confirmation or check number) overwrites it exactly as if it had been typed from scratch. See `src/engine/AutoComment.ts`.
